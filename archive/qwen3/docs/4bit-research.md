# witrans-4b：4bit 优化与研究方案

2026-09-30。用户选择4bit为后续主线。本方案区分已观测证据、已有研究和待验证假设，保持原始Qwen3-4B、一个统一adapter、非思考JSON协议及uv环境。

## 当前判断

同一开发集NF4端到端平均3.65秒，按保存输出重新分词约5.26 token/s，峰值张量分配2.87 GiB；不是纯解码速度，也不是硬件上限。当前链路是Transformers + bitsandbytes NF4 + 独立LoRA分支。CPU启动采用4个逻辑处理器、2线程以缓解尚未查明的原生崩溃，存在调度瓶颈的可能，尚无证据确认主因。

v2仅388条训练、192个来源组。NF4测试与同精度基础模型均为30通过/4轻微/6严重，只证明格式改善，没有证明整体语义改善。高精度模型也有语义错误，因此不能把全部问题归咎于量化。

本轮新增[6条开发样本诊断](../runs/nf4-diagnostic.json)，直接记录生成token数：原配置首token平均0.235秒、整句3.687秒、首token后约5.07 token/s；加载的504个LoRA参数张量为FP32。仅在内存将LoRA改为BF16，整句3.437秒、首token后约5.44 token/s，6条原始输出一致。基础权重始终NF4，未保存新权重。单轮、固定实验顺序和streamer同步会影响计时，这只是候选优化线索，不能宣称稳定提速或语义等价。后续应交错重复顺序并扩展开发集验证。

## 推荐的先后顺序

1. **测清速度。** 记录真实生成token ID数量、首token延迟、首token后的生成速度、端到端P50/P95、峰值分配/保留显存。短句和较长段落分开，同一提示词、样本、生成预算、预热、供电状态；设备和调度改动逐个对比。已有估算数据不覆盖这些指标。
2. **扩充独立语义。** 首阶段目标3000–5000条有审核记录的训练行，至少1500个独立来源组；反向、改写、语境变化归入同组。补足自然对话、多句指代、否定、条件、数量单位、术语和上下文消歧。已有冻结开发/测试不回流训练；新的优化轮次建立新的开发/测试划分。
3. **比较SFT与LoftQ初始化。** 保持数据、训练token预算、rank和学习率一致，单独改变初始化，先检查初始化耗时与峰值再训练。LoftQ不是把已有训练adapter直接覆盖一下；应该在新训练开始前应用。
4. **比较SFT与翻译偏好训练。** 收集同一原文的正确译文和流畅但含一个明确语义错误的译文，先复现CPO，再尝试下面的项目改进。偏好对也必须审核，拒绝把等义表述误标为错误。
5. **部署时比较4bit实现。** 训练继续用NF4；部署候选可评测llama.cpp的4bit GGUF，或兼容的AWQ/GPTQ + 优化kernel。先核实本机Windows、模型结构和Python调用兼容性。量化格式、分组尺度和保留高精度层不同，不能当作只换一个引擎的无损操作。

## 可直接参考的研究

| 文献 | 能解决的部分 | 对项目的用法与限制 |
|---|---|---|
| [QLoRA，2023](https://arxiv.org/abs/2305.14314) | NF4、双重量化及低显存LoRA训练 | 当前已采用主要量化路线；继续使用，但不据此保证4B翻译质量。 |
| [LoftQ，2023/2024](https://arxiv.org/abs/2310.08659) | 联合考虑量化和LoRA初始化，降低与原始权重的差异 | 优先做新训练的初始化对照；不是扩充语义知识的替代品。 |
| [CPO / ALMA-R，ICML 2024](https://arxiv.org/abs/2401.08417) | 用翻译偏好改善只模仿参考的SFT | 更贴近我们的语义错误；论文在其他模型和数据上的结果不等于本机4B收益。 |
| [Word Alignment as Preference，EMNLP 2024](https://aclanthology.org/2024.emnlp-main.188/) | 用词对齐偏好减少漏译与幻觉 | 为保留实体/数量等训练信号提供依据；论文也报告总体指标收益不一致，需兼顾自然度。 |
| [AWQ，MLSys 2024](https://arxiv.org/abs/2306.00978) | 依据激活保护重要权重通道，配合高效部署 | 可作为部署量化对照；校准只用训练来源，不能用冻结测试。 |
| [MARLIN，2024](https://arxiv.org/abs/2408.11743) | 高效低比特矩阵计算与推理kernel | 说明低比特速度依赖实现；论文加速比例不直接外推到4060 Laptop。 |
| [Sequence-Level Knowledge Distillation，2016](https://arxiv.org/abs/1606.07947) | 用教师完整译文监督学生 | 符合32B API只提供最终译文的现有约束；不要求教师隐藏状态或logits。 |

实现依据：[PEFT量化与LoftQ文档](https://huggingface.co/docs/peft/developer_guides/quantization)。当前安装PEFT 0.18.1含`replace_lora_weights_loftq`；此便利路径是单轮近似，和论文完整迭代不完全相同，需验证本机峰值。LoRA/SVD初始化可能比常规LoRA初始化更费资源。

CPO使用偏好项加正例似然项，不需要额外常驻参考模型，适合优先做本机试验；正负序列的激活和显存峰值仍要实测。依据为[原论文损失与消融](https://arxiv.org/html/2401.08417v4)。现有DPO实现也可能通过缓存参考概率等方式节省显存，因此不把“双倍显存”当成所有DPO实现的必然代价。

[llama.cpp官方实现](https://github.com/ggml-org/llama.cpp)提供4bit量化与NVIDIA CUDA kernel，是可测的部署候选；尚未在本项目安装或验收。GGUF是文件容器，NF4/AWQ/GPTQ是不同量化路线，不能混称为同一种4bit精度。

## 值得尝试的项目改进

研究问题：**相同数据和计算预算下，优先训练4bit容易混淆的语义关系，是否比随机扩充数据更有效？**

建议把“最小语义对照”与“量化差异选样”结合。这是待验证的组合方案，不宣称已有论文没有做过，也不声称已经取得新算法成果。

- 在新的训练候选池中采集NF4输出与教师译文；可对少量池内样本离线运行高精度模型来帮助发现差异，不作为最终部署的一部分。
- 差异只用于选样，不能把高精度输出自动当正确答案。由Codex核对原文、语境和关键约束后，保留正确/错误对。
- 错误译文每次只改变一个关键事实：主体与客体、肯定与否定、上限与下限、计量单位、条件边界或上下文词义。保持句法自然，避免模型只学会区分流畅和不流畅。
- 构造同一句多义原文在两个明确语境下的不同正确译文，以及不应改变译文的无关语境变体。相关版本同组划分，测量模型是否真正使用语境。
- 先采用现有CPO目标；若确有遗漏关键部分，再单独实验对译文关键片段增加监督权重。损失只作用于答案，JSON外壳和输入不成为偏好捷径。新增片段目标不冒称原版CPO。

示意（新构造，非原测试样本）：

原文：`Keep the total below 15 kilograms.`

正确：`使总重量低于15千克。`

错误：`使总重量不超过15千克。`

两句都自然，但`below`排除等于边界，而“不超过”包含等于。训练信号直接针对这个差别，不用大量数字替换把一个语义组伪装成许多来源。

## 如何判断是不是有效创新

| 实验 | 变化因素 | 对照要求 |
|---|---|---|
| A | 新数据上的标准NF4 QLoRA/SFT | 建立新基线 |
| B | A + LoftQ初始化 | 同数据、rank、训练token预算 |
| C | A后追加标准CPO | 同预算的继续SFT对照，防止把额外计算当算法收益 |
| D | C改用语义关键对照与量化差异选样 | 同数量随机偏好对、只语义选样、只量化选样三个消融 |
| E | D增加关键片段权重 | 与D同数据同计算；检查一般翻译是否退步 |

开发阶段先小规模筛选，选定方案后至少3个种子复验。测试只用于冻结方案的最终比较。报告配对语义判定与置信区间、严重错误率、语言方向、上下文反转成功率、JSON合法率、原文约束保留率和性能；自动指标作辅助，不能代替语义验收。

部署合并与重新量化也必须单独验收：`Q4(W + ΔW)`一般不等于`Q4(W) + ΔW`。先保存原模型和adapter，在新目录产出候选，保证训练与部署的数值变化有记录。

当前不优先引入第二个草稿模型或复杂推测解码：短句平均输出约20 tokens，收益需要覆盖额外模型加载、验证和调度成本。也不先做领域路由、多adapter或更换基础模型，以保持项目的统一调用约束。

## 已完成的首轮可行性验证

v3已落地NF4 CPO与同起点继续SFT对照：60个经Codex验收的偏好对、8次更新、一个种子。共同开发目标选择SFT对照，三组开发语义计数相同，未建立质量改善证据。更新次数和前向次数相同，但没有严格控制FLOPs。这轮证明8GB显卡可运行链路，尚不能验证论文效果或创新收益；LoftQ、量化差异选样和关键片段加权尚未实施。详见 [v3验收报告](../runs/v3-model-acceptance.md)。

## v5更新与后续编译试验

v5已完成678条/306来源组、85步NF4继续SFT。答案NLL降至0.66957，但已知200条开发集仅139条无错误通过；同口径起点也为139条，通过率差值0，来源组95%区间[−2.5,+3.0]个百分点。严重错误32条对35条，仍未通过开发晋级。不能把更低NLL当作可靠翻译的证据，见[v5完整验收](../runs/v5-model-acceptance.md)。下一步使用另80条经审核的原创多句训练材料挖掘实际错误，不复制已读测试。

性能方面，现有链路单轮开发仅约5.22输出token/s。静态KV缓存与`torch.compile`可减少动态形状和重复调度开销，这是值得实测的假设；依据是[Transformers4.57版本文档](https://huggingface.co/docs/transformers/v4.57.1/llm_optims)。文档的加速数字不能直接外推到本机NF4+LoRA。

已完成[只读编译环境检查](../runs/compile-runtime-probe.json)：torch2.10.0、Python3.12.12、bnb0.49.2，Python开发头文件和导入库可用，目前未装Triton。按[Windows Triton维护仓库的兼容表](https://github.com/triton-lang/triton-windows)，PyTorch2.10应匹配Triton3.6系列；其轮子可自带部分CUDA工具链和TinyCC，因此PATH上没有`cl`/`nvcc`本身不能证明GPU编译不可行。后续应使用独立uv运行环境验证，保持当前环境与默认部署配置可复现；尚未安装编译依赖或执行模型编译，不能宣称提速。
